## Problem Statement

PropYield currently has one customer model: branded partner tenants (mortgage companies/brokerages) who manage their own agents, tokens, and reports. Individual agents and investors with no partner relationship have no way to get their own access — the founder has to manually create a tenant for them via the superadmin panel, exactly as was done for Jerry Johnson under the founder's own GPM tenant.

## Demand Evidence

One named person: Jerry Johnson, an EXP realtor and long-time business relationship of the founder, was given a test account under GPM to try PropYield. His actual ask was to **brand it himself** and use it for his own investor clients — not anonymous/unbranded access. Broader evidence: multiple brokers the founder has talked to currently spend 30-60 minutes manually compiling investment data from 6-8 sources per report; PropYield's differentiator is speed, comprehensiveness, customizability, and some investment-analysis features not readily available elsewhere. This is real evidence PropYield's analysis is valuable — it is **not** yet evidence that a self-serve solo-signup flow specifically is the right wedge, since Jerry is n=1 and was manually onboarded, not self-served.

## Status Quo

Brokers/agents doing their own investor-report analysis today manually compile data from 6-8 sources per deal, costing 30-60 minutes per report. Individuals who want PropYield access specifically (like Jerry) currently have to ask the founder directly and get manually onboarded — there is no self-serve path.

## Target User & Narrowest Wedge

Target: Jerry Johnson — a credentialed, licensed agent who wants to present PropYield's output as his own analysis to his own investor clients. This is a credibility instrument, not a quiet personal tool: he won't send a report to a client unless it looks like his own work.

Narrowest wedge: a self-serve signup that creates a lightweight **solo branded tenant** (a `Tenant` row with exactly one admin `User`) — reusing the existing partner-tenant model at one-person scale, not a parallel anonymous/unbranded user system. Originally proposed as an anonymous unbranded flow (email-verify → 1 free token → minimum purchase to continue); reframed during this session once it became clear Jerry's actual ask was for his own brand, which the anonymous framing can't deliver.

## Constraints

- Tenant creation today only happens via the superadmin-only endpoint (`POST /api/super/tenants`), which also creates the first admin `User` — no public signup path exists.
- **Correction from an earlier draft:** there is no "$5 minimum purchase" anywhere in the shipped system. The real minimum is **$50** — the smallest shipped pack (`pack_10` = 10 tokens for $50, i.e. $5/token; `pack_100` = 100 tokens for $400 bulk rate). An earlier draft of this doc conflated the $5/token *unit* price with a $5 *minimum purchase amount*. Every reference to "$5 floor" below means the real $50 minimum purchase.
- Self-serve Stripe-based token purchasing for tenants already shipped (`docs/designs/self-serve-token-purchasing.md`), but only ONE Stripe primitive is actually reused: the hosted `mode=payment` Checkout Session + webhook-signature-verification pattern for the eventual token purchase itself. The card-on-file gate for the free token (Stripe SetupIntent, `mode=setup`, plus a Stripe Customer object to attach it to) is **net-new** Stripe integration work — there is no existing SetupIntent/Customer code in this repo to reuse. Effort estimates below account for this.
- Each report likely costs real Anthropic API spend, so the free-token gate must actually block abuse, not just look like it does.
- **Token balance target:** reports are debited against the acting `User.token_balance`, not `Tenant.token_balance` (existing partner-tenant flow separately allocates from the tenant pool to a user's balance via a distinct admin action — that indirection exists for multi-agent tenants and doesn't apply to a one-person solo tenant). The free-token grant and any solo-tier purchase must credit the admin `User.token_balance` directly, or Jerry can complete the entire signup flow and still be unable to generate a report.
- **Auth bootstrap:** `POST /api/signup/solo/complete` must return the same `{access_token, user}` shape as `POST /api/auth/login`, so the new admin lands in `admin.html` already authenticated — otherwise the flow stalls immediately after signup.
- **Abuse surface on both public endpoints:** unlike `POST /api/super/tenants` (superadmin-only, already checks slug/email uniqueness against `RESERVED`), both `/api/signup/solo/start` and `/api/signup/solo/complete` are public and unauthenticated. `/start` needs a rate limit (it creates a real Stripe Customer per call, a cheap Stripe-API-spam vector even before any card is entered); `/complete` needs slug derivation from the company/display name plus collision handling (e.g. append a numeric suffix), since it's the point where the Tenant row actually gets created and must not collide with `RESERVED` or an existing slug.
- **`RESERVED` and route ordering (eng-review finding):** `signup` is not in the `RESERVED` set (`server.py:859`) today, and `GET /{slug}/admin` (`server.py:1769`) doesn't check `RESERVED` at all — only the plain `GET /{slug}` catch-all does. Add `signup` and `login` to `RESERVED`, and declare the new `GET /signup` route (serving a new `solo-signup.html`) before the `{slug}` catch-alls in `server.py` — belt-and-suspenders: `RESERVED` blocks the slug at tenant-creation time, route order blocks it at request time.
- **Rate limiter backing store (eng-review finding):** neither Redis nor any counter-table pattern exists in this codebase, and this app is a single Vercel serverless function (`vercel.json`) — an in-memory rate limiter (slowapi's default) wouldn't share counts across cold starts/instances. Add `slowapi` backed by a new `RateLimitBucket` table in `web/database.py` (key, count, window_start) rather than Redis, reusing the existing Supabase Postgres connection instead of provisioning new infra for a low-volume endpoint.
- **No email verification.** Card-on-file is the sole gate for the free token; email verification is dropped from the original anonymous-flow proposal rather than layered on top, to keep the wedge narrow.
- **Charge mechanism for the eventual purchase:** the SetupIntent's saved card is used ONLY as an abuse gate for the free token — it is NOT charged automatically. The actual token purchase, when it happens, reuses the existing hosted Checkout Session **creation and signature-verified webhook receipt** identically to how partner tenants buy tokens today (see `docs/designs/self-serve-token-purchasing.md`). This avoids off-session charging, SCA, and decline-handling entirely, which would otherwise be a second wedge's worth of Stripe work. It is NOT fully "untouched," though: today's webhook handler (`_credit_tenant_tokens`) always credits `Tenant.token_balance`. For a `tier='solo'` tenant it must instead credit the single admin `User.token_balance` directly — a small, explicit branch on `tenant.tier`, not a separate payment path.
- **Webhook user lookup (eng-review finding):** Stripe metadata on the purchase Checkout Session only carries `tenant_id`/`token_count`, not a `user_id`. For a `tier='solo'` tenant, the solo-credit branch resolves the target user via `db.query(User).filter_by(tenant_id=tenant_id, role='admin', is_active=True).first()` — matching the single-admin invariant enforced elsewhere in this design. If no active admin is found (a deactivated account), log an error and leave the purchase recorded in `token_purchases` but uncredited, flagged for manual reconciliation, rather than silently crediting nobody — the same "never silently fail a paid purchase" bar the webhook already holds for signature/idempotency failures.
- **No orphan signup rows.** Nothing is written to the database until the card is verified. `POST /api/signup/solo/start` accepts the signup form (email, password, company/display name, color) and creates only a Stripe Customer + SetupIntent (`mode=setup`), returning its `client_secret` for the client to confirm the card via Stripe Elements — no Tenant/User row yet, so an abandoned signup leaves nothing behind to clean up or collide with a retry. `POST /api/signup/solo/complete` takes the confirmed `setup_intent_id` plus the original form fields, verifies server-side (`stripe.SetupIntent.retrieve`, synchronous check — no webhook needed for this step since the client is present and waiting) that its status is `succeeded`, and only then creates the Tenant(`tier='solo'`) + admin User in one transaction, grants the free token to `User.token_balance`, and returns `{access_token, user}`.
- **SetupIntent must be consumed, not just checked.** A `stripe.SetupIntent.retrieve().status == "succeeded"` check is durable and re-checkable indefinitely — without marking it used, the same verified `setup_intent_id` could be replayed against `/complete` repeatedly with a different email/company name each time, minting one free-token Tenant per call with zero additional Stripe friction. Store the `setup_intent_id` on the created `Tenant` (unique constraint) so a second `/complete` call for the same SetupIntent fails outright.
- **Solo tenants stay single-user by construction.** The webhook's solo-tenant crediting branch (below) assumes exactly one admin `User` per solo `Tenant`. **Eng-review correction:** TWO existing endpoints can create a second `User` under a tenant — `POST /api/admin/users` (`server.py:1260`) AND `POST /api/admin/invite` (`server.py:1286`), both gated only by `auth.require_admin` with no tier awareness. `/api/admin/invite` currently has no UI caller in `admin.html` but is still a live, reachable API — guarding only the first endpoint leaves this invariant breakable through the second. Both endpoints must reject the request (or hide the UI for it) when `current_user.tenant.tier == 'solo'`.
- **Card-reuse abuse (scoped out for this wedge):** nothing stops the same physical card being attached to a new Stripe Customer across repeat signups with disposable emails to farm multiple free tokens (Stripe card fingerprinting could detect this). Explicitly out of scope for Approach A — the Assignment tests with exactly one real person (Jerry) before this is a live product anyone could stumble on, so this residual risk is acceptable until real signup volume exists. Revisit with fingerprint dedup if abuse is observed.

## Premises

1. Real product = self-serve **solo branded tenant**, extending the existing `Tenant`/`User` model, not a parallel anonymous user type. — Agreed.
2. Demand evidence is real but thin: one named person (Jerry) + general market pain, not yet validated as the right specific wedge (a stranger completing a self-serve signup end to end). — Agreed.
3. Email verification alone is not enough to gate the free token — disposable emails defeat it trivially, and each free report costs real API spend. A card-on-file (Stripe SetupIntent, no charge) must gate the free token instead, per how the industry actually prevents this ([Stripe: free trial abuse prevention](https://stripe.com/resources/more/free-trial-abuse)). — Agreed.
4. **Revised during this session** (was: the $50-minimum-purchase floor is a settled business decision, out of scope). A Claude-subagent second opinion argued a solo agent's post-one-sample purchase psychology differs from a brokerage buying tokens in bulk, and immediate purchase friction right after a single free report risks killing activation for an unvalidated segment — and at the real $50 minimum (not the $5 this session initially assumed), that friction is materially larger, which strengthens rather than weakens the case for not just assuming the floor holds. Revised to: **keep the $50 floor, but instrument free-token → first-purchase conversion for solo tenants separately from existing partner-tenant purchases**, so there's real data before assuming the floor holds for this segment.

## Approaches Considered

### Approach A: Minimal solo signup, reuse everything — RECOMMENDED
Add a `tier` column to `Tenant` (`partner`/`solo`). Two new public endpoints: `POST /api/signup/solo/start` (creates a Stripe Customer + SetupIntent, returns `client_secret`, writes nothing to the DB) and `POST /api/signup/solo/complete` (verifies the SetupIntent succeeded server-side, then creates the Tenant + admin User in one transaction, grants the free token to `User.token_balance`, returns `{access_token, user}` like login does). Both endpoints call a shared `_provision_tenant_and_admin()` helper (see Code Quality below), also used by the existing `POST /api/super/tenants`, rather than duplicating Tenant+User creation logic. Reuse the existing `admin.html`/report engine/Stripe Checkout-Session purchase flow for any later purchase, with one small branch in the existing webhook handler so a `tier='solo'` tenant's purchase credits `User.token_balance` directly instead of the tenant pool.
**Eng-review correction:** "color swatch + initials placeholder" doesn't exist in this codebase — the actual no-logo fallback (`index.html:106-109`) renders PropYield's own icon, not an initials avatar. Since the entire premise here is Jerry seeing HIS OWN brand (not PropYield's), Approach A includes building a real initials-avatar component (a colored circle with the tenant's initials in `tenant.primary_color`) for `tier='solo'` tenants with no logo, replacing the PropYield-icon fallback. This is now scoped work, not assumed reuse.
Effort: S/M (larger than a pure "wire up an existing thing" S, since the Stripe Customer/SetupIntent flow, the rate-limiter table, the initials-avatar component, and the first integration-test harness for this codebase are all genuinely new work, not reuse — see Constraints and Dependencies). Risk: Low.
Pros: reuses the report engine, admin panel, and purchase Checkout-Session/webhook plumbing already built and tested; no orphan DB rows from abandoned signups; ships fast enough to validate with Jerry directly; the free-token report now actually shows Jerry's own color/initials, not PropYield's icon, so it demonstrates the real value prop the second opinion flagged.
Cons: no custom logo upload at signup (addable later via the existing branding tab), no dedicated solo-tier onboarding polish, the SetupIntent/Customer piece is real new surface (first Stripe Customer object in this codebase) that still needs its own testing pass, the webhook handler needs a small but real branch for solo-tenant crediting rather than being purely untouched, and this ships as a fully public endpoint even though the near-term Assignment only tests with one known person (Jerry) — considered and kept in scope (see Open Questions).

### Approach B: Full solo onboarding with logo + branding wizard
Same backend, but adds a guided multi-step signup wizard: logo upload, a live branded-report preview before signup completes, and a dedicated marketing landing page.
Effort: M. Risk: Medium.
Pros: maximizes the "see your own brand before committing" moment; more polished first impression.
Cons: real extra build (file upload/storage, validation, wizard UI) before validating anyone beyond Jerry wants this at all — the "build the platform before proving the wedge" trap this session's operating principles specifically warn against.
Rejected for now: not validated as necessary at n=1 evidence.

### Approach C: Manual-assisted solo onboarding (no self-serve signup yet)
Keep creating solo tenants manually via the existing superadmin flow, just formalize a `tier='solo'` template with standard default branding.
Effort: XS. Risk: Low, but doesn't test the thing actually in question.
Rejected: self-serve signup completion by a stranger is exactly what's unvalidated here — this approach never observes it.

## Recommended Approach

**Approach A.** Matches the narrowest-wedge premise, reuses the Tenant/User model and the Stripe plumbing already shipped, and — critically — still produces a genuinely branded artifact (color + company name on the report) so the free token can actually do its job of earning Jerry's trust to send to a client.

## UI/UX Specification (from /plan-design-review)

The `/signup` page and initials-avatar component were unspecified in earlier drafts (design completeness scored 2/10). Decisions made during design review:

**Signup page layout** — desktop: a co-equal two-column split, form on the left, a live branded-report preview on the right that updates as the visitor types their company name and picks a color. This makes the credibility-instrument premise (Jerry seeing HIS OWN brand) visible in the first 5 seconds, not something discovered after signup. Mobile (<640px): stacked, preview shown FIRST, form below — preserves the same priority rather than demoting it to screen width.

**Branding layers, kept distinct** — the signup page's own chrome (background, typography, form styling) reuses `admin.html`'s existing tokens (`--navy-deep`, `--gold-light`, `--brand`, Inter font) since this is a PropYield surface, classified as App UI/OPERATE (calm hierarchy, no hero, no generic SaaS card grid). Only the live-preview panel shows the visitor's own picked color/initials — a distinct visual island inside the PropYield chrome, not a page-wide reskin.

**Card-ask framing** — one line directly above the Stripe Elements card field: "We verify a card to prevent abuse — you won't be charged unless you choose to buy more tokens later." Addresses the trust risk of asking for payment info before any value is shown.

**Interaction states:**

| Feature | Loading | Error | Success |
|---|---|---|---|
| `/start` (Stripe Customer+SetupIntent) | Button shows spinner, disabled | Generic "something went wrong, try again" (rare — this is a server-side Stripe call) | Advances to card entry |
| Card entry / `/complete` | — | **Card declined:** inline error near the Stripe field (not a redirect), rest of the form (company name, color, email) stays filled in, CTA re-enables. Announced via `aria-live="polite"` region so screen readers hear it. | Advances to admin.html, already authenticated |
| Slug collision (numeric suffix appended) | — | N/A — never surfaced | Silent: success screen shows company name + branding, never the slug/URL |

**Initials-derivation rule:** first letter of the first two words (e.g. "Acme Investments" → AI, "Jerry Johnson" → JJ); a single-word name uses its first two letters (e.g. "Acme" → AC).

**Avatar text contrast:** compute relative luminance of `tenant.primary_color` and choose white or near-black (`#1a1a1a`, not pure black) text automatically — guarantees 4.5:1 contrast regardless of what color a tenant picks, rather than hardcoding white text (which would fail on light colors).

**Accessibility baseline:** 44px+ touch targets on the CTA and Stripe card field on mobile; `aria-live="polite"` for the decline error; visible labels (not placeholder-as-label) on all form fields.

**Deferred (not blocking):** no `DESIGN.md` exists for this project — recommend `/design-consultation` as a follow-up, not required before this ships, since the existing `admin.html` token system already gives this page a concrete, non-generic visual foundation to build from.

## Post-implementation updates

- **Rate limiter backing store — substituted, not literally `slowapi`.** The `limits` library `slowapi` wraps has no Postgres storage backend (only memory/Redis/Memcached/MongoDB), so wiring it to `RateLimitBucket` would have meant writing a custom `limits` storage adapter — more surface area than the actual goal (shared counts across serverless cold starts) requires. Implemented as a small `_check_rate_limit()` fixed-window helper directly against `RateLimitBucket` instead: same backing table, same design intent, no new dependency. `/api/signup/solo/start` is capped at 5/hour per IP, `/api/signup/solo/complete` at 10/hour per IP.
- **`GET /{slug}/admin` RESERVED check** and **`signup`/`login` added to `RESERVED`** — both eng-review findings from this doc — done as part of this change, ahead of `/signup` going live.
- **`_provision_tenant_and_admin()`** extracted from `POST /api/super/tenants` and shared with `/api/signup/solo/complete`, as specified.
- **Slug collision** resolved with a numeric-suffix loop (`acme`, `acme-2`, `acme-3`, ...) checked against both `RESERVED` and existing slugs — never surfaced to the visitor, per the UI/UX spec.
- **`tests/test_solo_signup.py` + `conftest.py`** — this codebase's first integration-test harness, per the Dependencies note. Uses an in-memory SQLite engine (patched onto the `database` module before `server` is imported) and a fake Stripe client covering the exact `v1.customers` / `v1.setup_intents` / `v1.checkout.sessions` surface `server.py` calls — no real Stripe or network access in tests. Covers: no DB rows written by `/start`, SetupIntent-not-succeeded rejection, full happy path (free token lands on `User.token_balance`, not `Tenant.token_balance`), replay protection, slug-collision suffixing, the solo-tier single-user guard on both `/api/admin/users` and `/api/admin/invite`, and the webhook's solo-vs-partner crediting branch (including the "no active admin" manual-reconciliation path).
- **Initials-avatar component** implemented as small duplicated JS helpers (`tenantInitials()` / `tenantAvatarTextColor()`) in both `index.html` and `solo-signup.html`, consistent with this codebase's no-build-step, inline-per-page-script convention rather than introducing a shared bundle.
- **Not yet run:** the actual Assignment — Jerry completing this flow end to end with a real card and a real client send. The endpoints, migration, and tests are in place; this still needs a live Stripe test-mode (then live-mode) pass and Jerry himself.
