## Problem Statement

IRES, a large rental asset manager / investor group, already uses PropYield to underwrite new acquisitions. They asked the founder for help with a different job: deciding, property by property, whether to **hold, sell, or cash-out refinance assets they already own**. The founder's open question was whether this justifies a separate product or a paid module inside PropYield.

**Decision:** build it inside PropYield as a new gated analysis type. Do not start a separate project.

## Demand Evidence

- IRES asked about pricing / signaled they would pay for this capability before anything was built. No amount or terms have been discussed. This is the strongest demand signal in the session, but it is a signal, not a commitment.
- IRES is already an active PropYield client for acquisitions, so the relationship and trust in PropYield's output already exist.
- **Unverified (not provided during session):** IRES's portfolio size, the hours they spend per property today, how often they review assets, and what price they have in mind. The founder took the suggested answer on every diagnostic question without adding numbers, so treat these as open until IRES confirms them (see Open Questions).
- n=1. No second asset manager has asked for this yet.

## Status Quo

IRES staff build hold/sell/refi decisions by hand in spreadsheets: pulling comps, market rents, and loan data per property. PropYield already automates the comps/rent/tax compile for acquisitions (the 6-8 source, 30-60 minute manual job documented in prior designs). The exact logic and outputs in IRES's spreadsheet are unknown.

## Target User & Narrowest Wedge

- **Buyer:** IRES leadership (asset manager / investor group), as a PropYield tenant.
- **User:** whoever at IRES runs the per-property review today (name not yet captured).
- **Wedge:** one report on one owned property that compares three paths side by side, using IRES's real numbers:
  1. **Hold:** projected annual cash flow and IRR over the hold horizon, based on actual rent/opex and current debt.
  2. **Sell now:** estimated value from comps, less selling costs, prepayment penalty, and loan payoff, giving net proceeds. Tax on gain is flagged for a CPA, not computed.
  3. **Cash-out refi:** new loan at a current rate and target LTV, cash out after payoff and costs, and new cash flow / DSCR.
- Portfolio batching and ongoing monitoring are explicitly **not** in the wedge.

## Constraints

- **Existing dispatch to reuse:** `/analyze` (`web/server.py:1808`) routes 12 report types through `SYSTEM_PROMPTS` (`web/server.py:758`), all sharing token debit, daily limit, tenant branding, lead logging, report email, and PDF/Excel export. The new report is a 13th type with key `hold`.
- **Numbers are computed in Python, not by the model.** LLMs are unreliable at amortization and IRR arithmetic, and these numbers drive a premium recommendation on real assets. A new pure module `web/owned_asset.py` computes every figure in the comparison table. The model receives those figures as fixed inputs and is instructed never to recompute or alter them. It writes the narrative, interprets the comps and market rent, and makes the recommendation. The model supplies exactly two estimates, both through web search: current market value (from comps) and current market refi rate. Each has a user override, and the report labels which source was used.
- **v1 loan scope:** a single amortizing loan (fixed-rate, or interest-only entered as the current rate with amortization term = 0). Prepayment penalty is captured as a dollar amount. ARMs, multiple liens, yield maintenance/defeasance formulas, and balloon modeling beyond "balance due at maturity" are out of v1. The report states this assumption in its assumptions block.
- **Tax treatment, per path (this is where the acquisition engine must NOT be reused as-is):**
  - **Hold:** the owner's current annual tax bill. No reassessment.
  - **Refi:** the same current bill. A refinance is not a transfer, so there is no reassessment.
  - **Sell:** no tax line in the seller's proceeds (property tax proration is ignored in v1). The existing tax engine may be called with `owner_occupied=False` only to produce a buyer-side note ("a buyer's post-transfer tax would be about $X/yr"), because this can affect sale price. That note is text context only and never feeds a Hold or Refi number.
  - **Current tax bill is required for `hold`** at both UI and server. There is no fallback to the tax engine for Hold/Refi, so reassessed taxes can't leak in by default.
- **Token cost is hardcoded to 1** in `/analyze` (`current_user.token_balance - 1`, and the 402 check is `< 1`). Replace with `REPORT_TOKEN_COST = {"hold": int(os.getenv("HOLD_REPORT_TOKEN_COST", "3"))}`, default 1 for every other type, used by both the balance check and the debit. Provisional default **3 tokens** until IRES confirms a price.
- **Token debit timing:** today tokens are debited before streaming and never refunded if generation fails (`except` branches at the end of `stream_response` only yield an error). For `hold`, keep the debit before streaming (prevents double-spend from concurrent requests), but **refund the N tokens** in both `except` branches when no report text was produced. Leave refund behavior for other report types unchanged in this change (a separate, pre-existing issue).
- **Daily limit:** a `hold` report counts as 1 run toward the tenant's `daily_limit`, like every other type. Cost is enforced through tokens, not the daily limit.
- **Superadmin:** exempt from token debit (existing behavior) and from the entitlement 403, so the founder can demo and QA on any tenant.
- **Gating must be server-side.** New column `Tenant.asset_analysis_enabled` (Boolean, default False). `/analyze` returns 403 for `analysis_type == "hold"` when the flag is off. Superadmin toggles it via `PUT /api/super/tenants/{tenant_id}` (`web/server.py:1713`) and `super.html`.
- **Server-side validation before any debit:** `hold` requests missing any required field return 422 before the token check, the Analysis log, or the debit.
- **Confidential owner data.** `/analyze` currently creates a `BuyerLead` row for every run and emails the full report text to the tenant sponsor contact, `REPORT_NOTIFICATION_EMAIL`, and every active tenant admin (`web/server.py:1891-1921`). For `hold`:
  - **No report emails** to `REPORT_NOTIFICATION_EMAIL` (the founder's inbox) or the sponsor contact. The report is not a buyer lead. Tenant admins may still receive it, since they are IRES.
  - The `BuyerLead` row is still created (the saved-reports list and delete flow depend on the `Analysis`/`BuyerLead` join at `web/server.py:1151`), with `buyer_name`/`buyer_email` left null. `report_text` is stored as today, so it inherits the existing tenant-scoped visibility and delete flow.
  - Raw owner inputs are **not** persisted as separate columns in v1. They exist only inside the generated report text. The `Analysis.asking_price` log column gets the current market value, not the loan balance.
- **Web search:** add `hold` to `WEB_SEARCH_TYPES` (`web/server.py:62`) so comps and current refi rates are live.
- **Deployment:** single Vercel serverless function (`web/vercel.json`), existing Supabase Postgres. The new column uses the same migration path used for `Tenant.tier` and `setup_intent_id`.
- **Not financial or tax advice.** The Sell path's capital-gains / depreciation-recapture / 1031 note is a flag to consult a CPA, not a computed number, consistent with the existing red tax disclaimer.

## Inputs

Owner inputs live in a nested Pydantic model, `OwnedAssetInputs`, attached to `AnalysisRequest` as `owned_asset: Optional[OwnedAssetInputs] = None`. Its field names are the column names of the future `OwnedProperty` table (Approach B), so v2 is a migration, not a rename.

**Two-call flow:**
1. **Estimate call** (only when `market_value_override` or `refi_rate_override_pct` is blank): a short, non-streamed call with web search and a `HOLD_ESTIMATE_SYSTEM` prompt that returns JSON only: `{"market_value": n, "refi_rate_pct": n, "comps": [...], "sources": [...]}`. The UI shows "Estimating current value..." while it runs.
2. Python runs `owned_asset.py` on the user inputs plus those two values (overrides win).
3. **Narrative call** (streamed, as today): `HOLD_SYSTEM` receives the computed table as fixed numbers and writes the report around it.

If the estimate JSON is missing, unparsable, or non-positive, the server does not guess. It returns "Could not determine current market value; enter a value override and re-run," skips the narrative call, and refunds the tokens. If both overrides are provided, the estimate call is skipped entirely.

## Premises

1. Build it inside PropYield, not as a separate project. It is the same engine asked a different question; a new product would duplicate tenants, auth, Stripe, tokens, comps, tax, and PDF for the same buyer. — Agreed.
2. It is a separate analysis **type**, not yet a separate **product**. Market it as "PropYield for owned assets" only after a second asset manager pays for it. — Agreed.
3. Monetize with a per-tenant entitlement flag plus a higher token cost per report, sold to IRES directly (invoice or token sale). No new self-serve Stripe subscription or self-serve unlock until a second buyer exists. — Agreed.
4. The report must use the owner's real numbers (loan, actual rent/expenses, current tax bill), not estimates. That is what makes it worth a premium over an acquisition report. — Agreed.
5. Portfolio batching and ongoing monitoring are out of v1. Single-property reports first; batch when IRES asks for it with a property count. — Agreed.

## Approaches Considered

### Approach A: New "Hold / Sell / Refi" report type (CHOSEN)
13th `analysis_type`, gated per tenant, premium token cost, with deterministic Python math for the comparison table. Effort S-M (human ~1.5 weeks / CC ~4-6 hrs, including the calc module, export, and tests). Low-medium risk. Reuses the `/analyze` pipeline, web search, report rendering, and PDF/Excel export. Tradeoff: owner numbers are re-entered on every run until asset records exist.

### Approach B: Owned-asset records + report
New `OwnedProperty` table per tenant; data entered or CSV-imported once, report re-runnable. Effort M (human ~3 weeks / CC ~1 day). Deferred, not rejected: the natural v2 once IRES runs properties regularly, and the foundation for batch and monitoring.

### Approach C: Paid concierge pilot
Hand-deliver 3-5 reports before writing code. Not chosen: IRES has already raised paying, and A is small enough that a real report is the better test of willingness to pay. C's main benefit (learning IRES's exact outputs) is captured by asking for their spreadsheet first (see The Assignment). Revisit C if IRES won't commit to a price before the build.

## Recommended Approach

Approach A:

1. **Data (`web/database.py`):** add `Tenant.asset_analysis_enabled` (Boolean, default False). No other schema change.
2. **Calc module (new `web/owned_asset.py`, pure functions, no I/O):**
   - `amortize(balance, rate_pct, months, periods)` returns the balance after N months and annual debt service (interest-only when `months == 0`).
   - `hold_projection(inputs, market_value)` returns per-year NOI, debt service, cash flow, exit value, exit selling costs, loan payoff at horizon, net exit proceeds, and levered IRR. Year-0 equity = market value − loan balance (opportunity-cost basis: what they'd get by selling today, before selling costs).
   - `sell_now(inputs, market_value)` returns gross value, selling costs, prepayment penalty, loan payoff, and net proceeds.
   - `cash_out_refi(inputs, market_value, refi_rate)` returns the new loan amount, payoff, closing costs, prepayment penalty, cash out, new debt service, new annual cash flow, and DSCR.
   - Each returns a dict that is the single source of truth for the table.
3. **Server (`web/server.py`):**
   - `OwnedAssetInputs` model plus `owned_asset` field on `AnalysisRequest`.
   - `HOLD_ESTIMATE_SYSTEM` (JSON-only estimate call) and `HOLD_SYSTEM` (narrative), with `hold` registered in `SYSTEM_PROMPTS` and `WEB_SEARCH_TYPES`. `HOLD_SYSTEM` writes valuation comps, market rent vs. actual rent gap, refi market context, risks, and a recommendation that references the server's computed numbers (supplied in the user message) without recomputing them.
   - `owned_asset_context(req)` builds the user message from owner inputs, labeling each value as user-entered or defaulted.
   - In `/analyze`: 422 validation for `hold` (first); 403 entitlement check; `REPORT_TOKEN_COST` for the balance check and debit; refund on failure for `hold`; skip founder/sponsor emails for `hold`.
   - Expose `asset_analysis_enabled` and the hold token cost in `GET /api/tenant/{slug}` (`web/server.py:1120`); accept the flag in `PUT /api/super/tenants/{tenant_id}`.
4. **Comparison table contract:** before streaming the narrative, the server emits a fenced JSON block `{"type":"hold_sell_refi","hold":{...},"sell":{...},"refi":{...},"assumptions":{...}}` built from `owned_asset.py` output, plus a rendered markdown table. `index.html` detects the block for structured rendering; if parsing fails, the markdown table still renders, so the report is never blank.
5. **UI (`web/index.html`):**
   - "Hold / Sell / Refi" report option, shown only when the tenant is entitled, with its token cost on the option ("3 tokens").
   - Owner-data intake section with required fields marked and defaults pre-filled and editable.
   - `exportExcel()` (`web/index.html:1639`) adds a "Hold-Sell-Refi" sheet from the JSON block.
   - PDF export (html2pdf config near `web/index.html:1630`) includes the rendered comparison table, following the existing section-toggle pattern.
6. **Super admin (`web/super.html`):** entitlement toggle per tenant.
7. **Tests (`tests/`, harness in `tests/conftest.py`):**
   - `owned_asset.py` unit tests against hand-checked cases: a fixed-rate amortization balance, interest-only, zero-balance (free and clear), IRR for a known cash-flow series, net proceeds with a prepayment penalty, and negative cash-out (refi doesn't cover the payoff).
   - `/analyze` `hold`: 422 on missing required field with no debit; 403 when not entitled; superadmin bypasses the 403 and the debit; debits 3 while other types still debit 1; 402 when balance < 3; tokens refunded when either model call raises or the estimate JSON is unparsable; estimate call skipped when both overrides are given; counts 1 toward the daily limit; no send to `REPORT_NOTIFICATION_EMAIL`/sponsor.
   - **Tax guard:** assert that for `hold`, `owned_asset_context()` and the calc module never call `property_tax.estimate_property_tax` for Hold/Refi figures, and that Hold/Refi tax in the table equals `current_annual_tax` (growing at `expense_growth_pct` in the Hold projection). The buyer-side Sell note is the only permitted engine call.
   - Flag round-trip through the super endpoint.

## Reviewer Concerns

### R2-1 — consistency

**Problem**

> The refund rule says hold tokens are refunded 'when no report text was produced' (Constraints, token debit timing). But Recommended Approach step 4 has the server emit the JSON comparison block and a rendered markdown table before the narrative streams. If report text includes that server-emitted table, a narrative-call failure always happens after text was produced, so the refund never fires in the main failure case the tests claim to cover ('tokens refunded when either model call raises').

**Remedy**

> Define the refund condition in terms of the narrative. For example, refund when the narrative call raises before it yields any model text, whether or not the server-emitted table was already sent. Make the test assert a refund after the table has been emitted.

### R2-2 — completeness

**Problem**

> Superadmin is exempt from the token debit, but the refund-on-failure behavior is unconditional for hold. A failed superadmin run would credit N tokens that were never debited, to the superadmin or the tenant.

**Remedy**

> State that the refund only reverses a debit that actually happened (for example, track a debited flag or amount), and add a test that a failed superadmin hold run leaves balances unchanged.

### R2-3 — consistency

**Problem**

> hold_projection defines year-0 equity as 'market value − loan balance (opportunity-cost basis: what they'd get by selling today, before selling costs)'. What an owner would actually get by selling today is sell_now's net proceeds, after selling costs and the prepayment penalty. The stated rationale contradicts the formula. The gross basis also overstates the initial investment and understates Hold IRR compared with Sell, which biases the recommendation.

**Remedy**

> Either set year-0 equity to sell_now net proceeds so it matches the stated rationale, or keep the gross basis and change the rationale to explain why it's used. Leave IRES's preferred basis as an open question (it already is) without leaving the formula and its rationale in conflict.

### R2-4 — completeness

**Problem**

> The calc module has no defined behavior for an underwater or zero-equity property (market value ≤ loan balance, or ≤ balance plus penalty), where year-0 equity is non-positive and levered IRR is undefined. It also has no behavior for IRR non-convergence or multiple sign changes. The unit tests cover free-and-clear and negative refi cash-out, but not these cases.

**Remedy**

> Specify what hold_projection returns when IRR is undefined or doesn't converge (for example, IRR = null with a reason string that the table and narrative display). Add unit tests for the underwater and non-convergent cases.

### R2-5 — completeness

**Problem**

> Hold and Refi NOI are built from actual_monthly_rent with no vacancy, credit-loss, or capital-reserve input. It isn't stated whether actual_annual_opex is meant to include reserves, so the Hold cash flows and Refi DSCR may assume 100% occupancy indefinitely.

**Remedy**

> Add a vacancy/credit-loss percentage (and optionally a capex reserve) with a stated default, or explicitly state that actual rent is treated as collected rent net of vacancy and that opex includes reserves. Show that assumption in the assumptions block.

### R2-6 — completeness

**Problem**

> The estimate-failure behavior only covers the market value ('Could not determine current market value; enter a value override'). The estimate call also runs when only refi_rate_override_pct is blank. The design doesn't say what happens when market_value is valid but refi_rate_pct is missing, unparsable, or out of range, or when market_value_override is given and only the rate estimate fails. The error message and the retry instruction would be wrong in those cases.

**Remedy**

> Define per-field validation of the estimate JSON, including a plausible range for the refi rate. Give each missing value its own error message that names the specific override to enter. State whether a missing rate blocks the whole report or only the Refi column.

### R2-7 — feasibility

**Problem**

> The flow runs a non-streamed estimate call with web search, then a streamed narrative call with web search, sequentially inside one Vercel serverless function. The design doesn't say whether the estimate call runs before the StreamingResponse starts or inside stream_response. It also doesn't address the function's maximum duration, or how the UI's 'Estimating current value...' state is driven. If the estimate runs outside stream_response, the refund 'in both except branches' of stream_response doesn't cover its failures.

**Remedy**

> Specify where the estimate call executes (preferably inside the streaming generator, emitting a status event the UI uses for the 'Estimating...' state). Confirm the combined latency fits the configured Vercel maxDuration (and state that value), and make the refund path cover estimate-call exceptions and timeouts.

### R2-8 — clarity

**Problem**

> Analysis.asking_price is set to the current market value, but when no override is given that value exists only after the estimate call. The design says 422 happens before the Analysis log, but doesn't say whether the Analysis row is written before or after the estimate call, or what asking_price holds when the estimate fails and the tokens are refunded.

**Remedy**

> State when the Analysis/BuyerLead rows are written relative to the estimate call, and what is recorded (or whether any row is written) for hold runs that fail and are refunded.

### R2-9 — completeness

**Problem**

> Server-side validation only covers missing required fields. Values that are present but invalid are not rejected before the debit and would produce meaningless math: negative balance or rent, interest rate or LTV above 100, hold_years of 0, negative growth rates beyond a sane bound, or a negative market_value_override.

**Remedy**

> Define range constraints on OwnedAssetInputs (Pydantic Field bounds) that return 422 before the debit, and add a test for at least one out-of-range value.

### R2-10 — completeness

**Problem**

> The v1 loan scope mentions 'balance due at maturity', but there is no loan maturity input. Interest-only is modeled as remaining_amort_months = 0 with no end date. The Hold projection can't tell whether an interest-only or balloon loan matures inside the hold horizon, so it may present a Hold path that silently requires a refinance.

**Remedy**

> Either add an optional loan maturity (months remaining) field that the Hold projection uses to flag or pay off a balloon inside the horizon, or state that v1 assumes the loan doesn't mature within hold_years and print that in the assumptions block.

### R2-11 — consistency

**Problem**

> The Inputs table lists paths that don't match the calc functions. interest_rate_pct is listed for 'Sell (payoff at horizon)' and remaining_amort_months for 'Sell', but sell_now uses today's balance and the horizon payoff belongs to the Hold exit. prepayment_penalty is listed for Sell and Refi only, and it isn't stated whether the Hold exit also deducts it.

**Remedy**

> Correct the Path(s) column to match the calc function signatures (the rate and amortization feed the Hold projection and horizon payoff). State whether a prepayment penalty applies at the Hold exit.

### R2-12 — clarity

**Problem**

> The three columns report different metrics: Hold gives a multi-year IRR, Sell gives net proceeds today, and Refi gives cash out plus a single-year cash flow and DSCR. Refi has no horizon projection or IRR, so there is no common basis for comparing the paths, and the model's recommendation must weigh figures that aren't comparable.

**Remedy**

> Either add a Refi-then-hold projection over hold_years (IRR and exit proceeds) so all paths share a metric, or state explicitly that the recommendation weighs these different metrics qualitatively and list the decision factors HOLD_SYSTEM is told to use.

### R2-13 — completeness

**Problem**

> Persisting from R1-6: the export and JSON-contract work is now in the approach and the effort estimate, but the tests still don't cover it. No test checks that the emitted JSON block matches owned_asset.py output, that the Excel 'Hold-Sell-Refi' sheet is built from it, or that the markdown fallback renders when parsing fails. The inner hold/sell/refi/assumptions keys are also shown only as {...}.

**Remedy**

> State that the block's inner keys are exactly the owned_asset.py return dicts (or list them). Add tests for block emission and equality with the calc output. Add at least a manual or JS check for the Excel sheet and the parse-failure fallback.

### R2-14 — clarity

**Problem**

> 'Tenant admins may still receive it' leaves it undecided whether hold reports are emailed to tenant admins. The report text will also contain the raw fenced JSON block, and the design doesn't say how that appears in emails or in saved reports reopened from the list.

**Remedy**

> Decide whether tenant admins are emailed hold reports. State whether the JSON fence is stripped (or rendered) in emails and saved-report views.
