## Problem Statement

PropYield's underwriting reports (comps, rental comps, financial projections, demographics) currently either omit property tax or would show it using the seller's current bill — which is wrong for an investor buyer in most states, since a sale can trigger reassessment, a homestead-exemption loss, or (in Michigan) an uncapping of taxable value that only applies to non-owner-occupants. An uncommitted tax-estimation engine already exists to fix this, built to Michigan's official Property Tax Estimator model and generalized to a 50-state rules table, but it is ahead of validated demand outside Michigan.

## Demand Evidence

- A specific PropYield test user (a realtor) told the founder directly that tax accuracy was needed — not an inferred assumption, a direct request.
- Founder's stated position, from 20 years of real-estate experience: "Getting the tax payments correct after acquisition is going to be a major factor for property analysis in all 50 states... I know this for a fact. Making this tool as accurate as possible is what gives it value." Treated as a settled domain fact, not requiring further user validation.

## Status Quo

The realtor test user currently does a manual, county-by-county lookup per deal to sanity-check tax accuracy — cross-referencing homestead vs non-homestead rates and the uncapping math by hand.

## Target User & Narrowest Wedge

Target: real-estate agents and investors using PropYield to underwrite an acquisition, starting with the confirmed Michigan-based test-user realtor.

Narrowest wedge (when pushed): Michigan-only, homestead vs investor split — the exact case that already has real millage data and a real user request. The founder built past this wedge into a full 50-state engine before validating the wedge itself; that gap is a design decision this doc addresses (see Recommended Approach).

## Constraints

- Only Michigan currently has real imported jurisdiction-level millage data (`method: "millage"`); every other state runs on `state_fallback` — a statewide median rate. **Correction from an earlier draft:** the fallback is not uniformly "low confidence" — `web/taxdata/state_rules.json` labels it `high` for 27 states (statutory constants), `medium` for 20 (published medians), and `low` for only 4. So the real gap this doc addresses is `method` (millage vs. state-median), not `confidence` — a state-fallback number can already be a trustworthy statutory constant; what it can't be is jurisdiction-specific.
- County-level millage data is fragmented and manually published almost everywhere outside Michigan — there is no single federal source.
- The tax module is not a standalone product; its value is entirely in service of the bigger acquisition-analysis report.

## Premises

1. The differentiator is not "we show property tax," it's "we show what the tax becomes for THIS buyer after transfer" — competitors (per landscape check below) don't appear to model reassessment-on-transfer explicitly.
2. Tax accuracy mattering broadly, not just in Michigan, is treated as a settled domain fact per the founder's experience — not something requiring further user validation.
3. The founder explicitly kept the "coverage is the binding constraint" framing after it was challenged (see Cross-Model Perspective) — observation of the one confirmed user should happen in parallel with coverage expansion, not gate it.
4. This module's value is entirely in service of the bigger acquisition-analysis product, not something to market or price standalone.

**Approach ruled out during the session:** Freezing scope at "Michigan-only, ship now" (Approach A) — rejected because it shelves the 50-state investment already made and doesn't match the founder's conviction that accuracy matters everywhere now, not just where a user has already asked.

## Approaches Considered

### Approach A: Michigan First, Ship Now
Cut the UI/report over to Michigan-only immediately; keep the 50-state engine code but gate other states behind a flag until each has real millage data. Fastest to real feedback, lowest risk, but shelves work already done and doesn't match the founder's conviction. **Rejected** — see Premises.

### Approach B: Systematic Coverage Pipeline
Treat the fallback rate as deliberately temporary. Build out the semi-automated per-state millage import pipeline (`scripts/import_millage.py` already exists) and set a coverage roadmap prioritized by where PropYield's actual users/deals are. Matches the founder's conviction; risk is that county millage data is fragmented and manually published almost everywhere, making this an ongoing data-ops job rather than a one-time build.

### Approach C: Confidence as a Feature, Users as the Data Engine
Surface the high/low confidence tier (already modeled in `TaxEstimate.confidence` and `.warnings`) directly and prominently in the report as a trust signal, and add a lightweight "submit your county's rate" flow so agents/investors in other states expand coverage themselves — self-prioritized by wherever users actually are.

## Recommended Approach

**B+C hybrid.** The founder's conviction rules out freezing at Michigan-only, but manually sourcing authoritative millage data for 50 states is a large, ongoing data-ops burden for one founder to carry alone. Approach C's crowdsourcing overlay makes B tractable: PropYield's own users, wherever they are, become the mechanism that expands real (not fallback) coverage, prioritized automatically by where deals are actually happening — rather than the founder manually importing states no one is using yet.

Concretely:
- Keep and extend `scripts/import_millage.py` as the founder-driven import path for high-volume states.
- Surface `TaxEstimate.method` in the report UI so users always see whether a number is jurisdiction-specific (millage) or a statewide median (fallback) — this is the real distinction, not the fallback's own `confidence` tier (see corrected Constraints above). **Already built**: `web/index.html` already renders this as a "Local millage rates" vs "Statewide estimate" badge, state-agnostically, wired through `/api/tax/estimate` — it's sitting uncommitted, not still to be designed. Success Criterion #3 below is largely satisfied on day one once this ships; the remaining 30-day work is coverage growth, not UI surfacing.
- Add a "submit your county's rate" flow, gated to logged-in PropYield users (not the open public web, to bound the abuse surface). Submissions land in a new `MillageRateSubmission` table (status: pending/promoted/rejected), carrying the same fields as `MillageRate` — county, jurisdiction, school district, homestead mills, non-homestead mills, tax year, source — plus the submitting user's account id (this is what makes a second submission "independent": a different account id on the same jurisdiction/year). A submission never jumps straight to `method: "millage"`; it stays `pending` (surfaced as `state_fallback` in the meantime, at the "low" floor regardless of that state's existing fallback tier) and is promoted into `MillageRate` only when a second independent submission for the same jurisdiction/year/mills-type agrees within 2% relative difference of the mill rate itself, or the founder manually confirms it against a public source and promotes it directly. Promotion is per mills-type (homestead and non-homestead can promote independently onto the same jurisdiction/year row), reusing `import_millage.py`'s idempotent upsert-by-key logic rather than a naive insert. A submission for a jurisdiction/year that already has a promoted rate (an annual refresh or correction) goes through the same agreement/confirmation gate as first-time coverage — no fast path yet.
- Given today's single confirmed user, expect nearly all early promotions to route through founder manual confirmation, not the 2%-agreement path — the crowdsourcing mechanism only starts relieving that bottleneck once submission volume exists. Success Criterion #2 below assumes the founder-confirmation path for its 30-day window, not organic agreement.

**Scope flag:** this recommendation extends the original problem (report tax accuracy) into a second, distinct engineering surface — a gated data-submission and trust pipeline (new table, promotion logic, admin confirmation workflow). That is a real, larger bet than a report-accuracy fix, made deliberately here because the founder's conviction rules out staying Michigan-only; it should be scheduled and reviewed as its own scope, not folded silently into "the tax feature."

## Open Questions

- Year-over-year rate refresh (mills are set annually) — the 2%-agreement rule handles first-pass conflict detection but not staleness of a previously-promoted rate.
- Input validation for the submission form — `import_millage.py`'s `--rates-are-percent` flag shows mills-vs-percent confusion is already a known error mode for a trusted CLI; a user-facing form needs the same guard.
- The exact admin workflow for "founder manually confirms" — an admin UI, or reuse of `import_millage.py` against a one-row CSV — not decided.
- What happens to an in-flight report if a submitted rate is later rejected during verification — held as pending and excluded, or shown and corrected later? Not designed yet.

## Success Criteria

- The realtor test user actively uses the Michigan tax estimate in a live deal without the founder walking her through it.
- At least one additional state gains real (non-fallback) millage coverage via either founder import or user submission within 30 days of this doc.
- Report UI clearly distinguishes millage-backed (`method: "millage"`) numbers from statewide-fallback (`method: "state_fallback"`) numbers in every state, not just Michigan — regardless of the fallback's own confidence tier.

## Dependencies

- `web/property_tax.py` (engine), `web/database.py` (`MillageRate` table), `web/server.py` (`/api/tax/estimate`, report integration), `scripts/import_millage.py` (bulk import), `web/taxdata/state_rules.json` (50-state rules, confidence tiers verified: 27 high / 20 medium / 4 low), `tests/test_property_tax.py`.
- New: a `MillageRateSubmission` table, the gated submission UI, the promotion logic, and an admin confirmation workflow — none of this exists yet.

## Reviewer Concerns

After 3 rounds of adversarial review plus a /plan-eng-review pass, all identified items were resolved except one open strategic risk:

- **Resolved:** `/api/tax/jurisdictions` (server.py) was missing its auth dependency — anyone could enumerate imported jurisdiction data without a token. Fixed: added `current_user: User = Depends(auth.get_current_user)`.
- **Resolved:** `mills_for()` in `web/property_tax.py` silently substituted the other rate when one side of a millage record was missing (homestead-only or non-homestead-only imports, which `import_millage.py` explicitly permits). Fixed: `estimate_property_tax()` now appends a warning when this fallback fires; covered by 3 new tests in `tests/test_property_tax.py`.
- **Open:** the "30 days, one additional state" success criterion assumes a second state has an equivalently-shaped per-jurisdiction CSV source (homestead vs non-homestead split, like Michigan's PRE/non-PRE). That hasn't been scouted. Most other states differ structurally (e.g. differing assessment ratios on a single millage rate, not two rates) — `import_millage.py`'s schema and docstring don't yet document how to handle that shape. Not blocking Michigan-only work; worth a spike before committing engineering time to a second state.
