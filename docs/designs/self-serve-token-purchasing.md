## Problem Statement

PropYield tenants (mortgage/brokerage partners like Success Group Mortgage, GPM, Vantage Realty Group, and Mitten Loans) each hold a `token_balance` pool that the tenant admin doles out to their agent/realtor users. There is no self-serve way for a tenant to add tokens to that pool — only the founder (superadmin) can top it up, via direct DB or admin-panel access.

## Demand Evidence

Tenant admins have proactively emailed/texted the founder asking for more tokens *before* running out — a repeated, real workflow, not a hypothetical. It has not yet escalated to a hard blocking crisis mid-deal, but the manual ask-and-wait pattern is already happening on its own, unprompted.

## Status Quo

A tenant admin notices they're getting low, contacts the founder directly, and the founder manually updates `tenant.token_balance` in the DB/admin panel. Cost: founder's time on every top-up, latency between ask and fulfillment, and the founder as a single point of failure in his own revenue loop.

## Target User & Narrowest Wedge

Target: the tenant admin (e.g. Jim at Success Group Mortgage, Teressa at Vantage Realty) who currently has to text/email the founder to get more tokens.

Narrowest wedge: a fixed-pack "Buy Tokens" button on the existing tenant-admin panel, one-off Stripe Checkout payment, no subscription and no auto-refill. The founder's first instinct was auto-refill (saved card + auto-charge below a threshold) — pushed back on and dropped once it became clear the only evidence supports manual purchase intent, not auto-charge intent. Auto-refill is a fast-follow to earn once manual-purchase behavior is observed, not the starting point.

## Constraints

- No Stripe (or any payment provider) dependency exists yet — confirmed absent from `requirements.txt` and `.env.example`.
- Stack: FastAPI + SQLAlchemy + Postgres (Supabase in prod), deployed on Vercel. Tenant-admin surface is `web/admin.html`; session auth already in `web/auth.py`.
- Tokens are purchased at the **tenant** level, matching the existing allocation model (tenant pool → `PUT /api/admin/users/{id}/tokens` moves balance from tenant pool to an individual agent).
- Pricing/margin *strategy* per token pack is explicitly out of scope for this design — only the payment plumbing is being designed here. Implementation still needs at least one concrete placeholder pack (token count + price) to create a real Stripe Price object; that number is a placeholder pending a separate business decision, not a design commitment.

## Approaches Considered

### Approach A: Minimal Stripe Checkout + webhook — RECOMMENDED
One button on `admin.html` opens a Stripe Checkout Session for a hardcoded fixed pack; a webhook credits `tenant.token_balance` atomically, logged to a new `token_purchases` audit table keyed by Stripe session id for idempotency. Reuses existing `admin.html` + `auth.py`.
Effort: S. Risk: Low.
Pros: ships fastest, Stripe owns all PCI/compliance, gives an audit trail that doesn't exist today.
Cons: pack sizes/prices hardcoded (a real deploy to change), no receipts beyond Stripe's own emails.

**Implementation notes (from adversarial review):**
- `token_purchases` columns: `id`, `tenant_id` (FK), `stripe_session_id` (unique), `token_count`, `amount_cents`, `currency`, `status`, `created_at`.
- `POST /api/tenant/checkout` derives `tenant_id` from the authenticated session (`auth.py`), never from client input — a tenant admin must not be able to credit a different tenant's balance. Checkout Session sets `success_url`/`cancel_url` back to `admin.html` with a query flag the page uses to show a confirmation/refresh state.
- The webhook route is exempt from normal session-auth middleware (Stripe calls it without a session cookie) and instead authenticates purely via Stripe signature verification — this must read the raw request body (`await request.body()`) *before* any JSON parsing, since signature verification fails against a re-serialized body. Confirm Vercel's ASGI adapter preserves raw bytes to this handler.
- The `token_purchases` insert and the `tenant.token_balance` increment happen inside one DB transaction. On webhook retry, a unique-constraint conflict on `stripe_session_id` means "already credited" — return 200 without re-crediting, never re-run the increment.
- `checkout.session.expired` and card-decline cases are left entirely to Stripe's own hosted Checkout UI/emails — no custom handling needed for the wedge.

### Approach B: Ledger-backed, configurable packs
`token_purchases` becomes the source of truth (balance derived from it), pack sizes/prices become superadmin-configurable data instead of hardcoded, plus a purchase-history view.
Effort: M. Risk: Medium.
Pros: full reconciliation/audit trail, lets pricing be experimented with without a redeploy, sets up cleanly for future auto-refill.
Cons: real added surface area (ledger consistency, admin CRUD) before anyone has proven a need for pricing flexibility.
Rejected for now: over-built relative to the validated wedge — no evidence yet that configurable pricing is needed.

### Approach C: Stripe Payment Links + invoice fallback
Skip a checkout-session endpoint entirely — use Stripe's no-code Payment Links (one per pack) as plain buttons, plus a manual "request an invoice/ACH" fallback for B2B buyers who prefer that over a card.
Effort: S (smaller than A). Risk: Low, but rigid — changing pack contents means recreating links, and the invoice fallback reintroduces the exact manual work this design is trying to remove.
Rejected for now: the invoice fallback undermines the point of self-serve, and link rigidity isn't worth the small effort savings over Approach A.

## Recommended Approach

**Approach A.** Matches the agreed narrowest-wedge premise exactly, reuses all existing plumbing (`admin.html`, `auth.py`, `Tenant.token_balance`), and produces real purchase-behavior data before investing in ledger/configurable-pricing complexity (B) or industry-specific payment rails (C) that aren't yet validated as necessary.

## Post-implementation updates

- **Pricing set** (was a placeholder): $5/token standard rate, $4/token bulk rate at 100 tokens. Packs: `pack_10` (10 tokens, $50) and `pack_100` (100 tokens, $400).
- **Discovered during live testing:** the Stripe account has "Managed Payments" (Stripe as merchant-of-record, handling global tax compliance) enabled by default, which blocks Checkout Session creation without a product tax code. Deliberately disabled per-session (`managed_payments: {enabled: false}`) rather than assigning tax codes — enabling it would make Stripe the legal seller and take on tax remittance, a business decision well beyond this wedge's scope. Revisit explicitly if/when automated multi-jurisdiction sales tax handling is wanted.
- **Webhook secret configured** in `web/.env` (test mode) pointing at `https://propmind.ai/api/stripe/webhook`.

## Reviewer Concerns (round 2) — resolved in implementation, not doc iteration

The user moved straight to building before a third review round. These were addressed directly in code rather than in the doc:
- Webhook must handle `checkout.session.async_payment_succeeded`/`async_payment_failed`, not just `checkout.session.completed`, gated on `payment_status` — done, per Stripe's own fulfillment guidance (`stripe-best-practices` skill).
- Checkout endpoint role-gated to tenant admins specifically (`auth.require_admin`), not just any authenticated tenant user — done and covered by an automated test (non-admin gets 403).
- Atomic crediting + idempotent retry (unique constraint on `stripe_session_id`, `IntegrityError` → rollback, no re-credit) — done and covered by an automated retry test.
- Raw-body signature verification confirmed to work on this stack (plain FastAPI `Request.body()`, no body-consuming middleware) — verified against a real Stripe test-mode Checkout Session and a correctly-signed webhook event, both over HTTP via `TestClient`.
- `stripe.Webhook.construct_event()` returns a `StripeObject`, not a dict — `.get()` on it raises `AttributeError` even though subscript access works. Caught by testing before it could hit production; fixed by calling `.to_dict()` immediately after extracting the event object.
- Never pass `payment_method_types` (per `stripe-best-practices`) — omitted, so Stripe's dynamic payment-method selection applies.
- Redirect-race UX (webhook may credit after the success-page redirect) — `admin.html` shows "tokens will appear within a minute" rather than claiming an instant balance update.
